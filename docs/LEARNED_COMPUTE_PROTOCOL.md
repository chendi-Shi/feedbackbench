# 学习计算预算控制器：实验计划

**本页是实验设计，实际执行状态以机器可读 protocol、status 和 report 为准。** 目录检查和协议单元测试不代表模型训练、采集或评测已经完成。运行前由实验 runner 冻结实际存在的协议、采集、学习、采样及评测源文件；工程修订保留原协议与源快照。

研究问题是：在冻结的预训练视觉语言动作模型上，学习每个决策应使用 2、4 或 10 次去噪计算的选择策略，能否在未参与训练的任务上取得更好的任务成功率与实际计算开销折中。控制器是新增学习组件；基础 VLA 保持冻结。动作与预处理接口沿用已有实现，新增算法及评测分别使用新的源文件和输出目录。

## 本机任务目录与数据边界

[`scripts/budget_protocol.py`](../scripts/budget_protocol.py) 仅用 Python 标准库读取本机安装包：

- `.venv/Lib/site-packages/libero/libero/benchmark/libero_suite_task_map.py`：AST 读取官方任务映射。
- 同目录 `__init__.py`：AST 读取默认 `task_orders[0]`，必须为 0–9。
- `bddl_files/<suite>/<task_key>.bddl` 与 `init_files/<suite>/<task_key>.pruned_init`：记录文件 SHA-256、相对路径和初态档维度。仅检查 pickle opcode，绝不执行 pickle 或导入 Torch/LIBERO。

范围为 `libero_spatial`、`libero_object`、`libero_goal`、`libero_10` 四个 suite，各取全部 10 个官方任务。每个 suite 原始任务编号 0–4 为 train，5 为 tuning，6 为 calibration，7–9 为 test。已有项目反复使用的四个 task 1 均留在 train，不能作为新的留出任务。

划分检查将**相同 BDDL 字节 SHA-256，或完全相同的标准化 benchmark language** 合并成连通组。标准化仅含 Unicode NFKC、casefold 和空白折叠，不使用语义相似模型。若一组触及多个原始划分，整组移到 train，再重算所有计划分母。同划分的重复任务保留各自官方条目，但报告统计按组聚合。

当前本机只读检查得到 40 个精确匹配组，没有触发重分配；全部初态档包含 50 条初态，索引 41、43 可用。**这不证明有 40 个独立语义任务**，同一 suite 仍共享场景、物体和操作结构。

| 划分 | 当前任务条目 / 精确匹配组 | 用途 | 初态 |
|---|---:|---|---|
| train | 20 / 20 | 学习参数与训练统计量 | 0、1 |
| tuning | 4 / 4 | 选择超参数 | 0、1 |
| calibration | 4 / 4 | 冻结校准规则与随机基线概率 | 0、1 |
| test | 12 / 12 | 最后评测，不参与训练或校准 | 41、43 |

测试标签、测试成功率和测试动作误差均不得进入控制器训练、特征标准化、超参数选择、校准或训练种子选择。划分单位是完整任务组，不能把一条轨迹的控制步随机拆到不同集合。旧轨迹不能重命名为新的独立任务。

## 采集和学习

train、tuning、calibration 共 28 个任务，每个采集两条行为轨迹：初态 0 使用固定预算 2，初态 1 使用固定预算 10。每次采集决策均在**同一观察、同一模型上下文和同一初始噪声**上计算 2、4、10 的配对预测，供新控制器学习与校准。

两条行为轨迹使用不同初态，所以它们不是预算 2 对预算 10 的配对因果实验。配对证据仅来自同一决策的三组预测；离线预测误差本身也不是任务成功率，最终仍需留出任务的真实闭环评测。采集过程中为生成监督信号付出的额外计算应单独记账，不得算成部署节省。

三个训练种子固定为 0、1、2，每个种子训练 `full`、`no_probe`、`proprio_probe` 三个特征版本。具体监督目标、架构、优化器、校准阈值及共享首步采样的计算记账必须随学习/采样源文件冻结；本任务目录模块不假定尚未完成的源文件已有哈希。

## 留出任务对照

| 方法 | 个数 | 约束 |
|---|---:|---|
| 固定预算 2、4、10 | 3 | 相同留出任务、初态和模型接口 |
| 学习控制器 `full`，种子 0、1、2 | 3 | 三个种子均报告，不按测试结果挑选 |
| 概率随机混合，种子 0、1、2 | 3 | 概率仅由对应 `full` 控制器在 calibration 上的预算频率确定 |
| `no_probe` 与 `proprio_probe`，各三个种子 | 6 | 保持训练划分与评测任务一致 |
| 合计 | 15 | 每种方法 12 个任务 × 2 个初态 |

当前计划为 **56 条采集轨迹 + 360 条评测轨迹 = 416 条轨迹**。一旦精确重复检查改变划分，协议自动报告调整后的实际数字，不能沿用该名义总量。概率随机混合用于区分观察条件下的学习选择与仅改变预算分布；不能根据测试轨迹事后调概率。

主报告应同时提供任务成功率、真实 NFE、决策与整条轨迹用时、控制器额外用时、预算频率和资源中断数量。统计按留出任务组聚合，同一任务/初态比较不同方法；置信区间以任务组为重采样单位，不能把大量相邻控制步当作独立样本。尚未完成的计划只能报告 partial，不得发布完整计划的收益结论；资源中断与已完成但失败的任务分开记录。

## 执行期限与资源

仅使用这台电脑，CPU、零云费用、无 GPU，同期最多一个实验 worker。截止时间固定为 **2026-10-30 06:08:00 UTC（北京时间 14:08）**；截止时保存已有记录并停止，不能通过不断新增方案延长预算。

v2 运行门槛为所属进程树 RSS 求和上限 5.5 GiB、系统可用内存下限 0.75 GiB、启动前可用内存至少 5.25 GiB。Windows venv 的启动器与实际 Python worker 分开，监控包括已观察到的后代进程；RSS 求和不代表去重后的物理内存。v1 的 4 GiB 启动门槛在首次集成时不足，worker 在第一条策略动作前停止，未产生训练轨迹。v2 保留该记录并提高启动门槛，研究算法、任务划分和期限均不变。资源门槛不承诺全部 416 条轨迹一定能完成；报告保留超时、资源阻断和未完成数量。

`task_catalog(root)` 返回包含官方任务、语言、BDDL/初态档哈希、划分和重复组的记录；`make_protocol(root)` 返回 JSON 可序列化字典，均不启动模型、不写实验目录。`source_binding.status=pending_runner_freeze` 明确区分计划和最终冻结凭证。目录中的 `case_id` 是逻辑标识；Windows 实际目录名由 runner 使用其摘要生成，避免冒号等文件名限制。

v2 在首个上下文与首速度计算后也因系统可用内存降到 0.728 GiB 停止，仍为零策略动作。v3 单独冻结并保留 v2；在每条轨迹的模拟器 reset 后、第一次推理前，对真实 worker 自身执行一次 Windows 工作集回收，记录前后 RSS/private/free 和耗时，不触碰其他进程。所有方法采用同一流程，原内存护栏不变；页重新载入产生的后续延迟计入推理和回合时间。RSS 降低不等于释放同量物理内存或提交内存，也不构成稳定运行保证。

协议模块验证见 [`tests/test_budget_protocol.py`](../tests/test_budget_protocol.py)，覆盖默认任务顺序、重复组传递性与泄露防护、调整后的分母、初态边界、15 种方法覆盖、资源/期限契约及不导入模型依赖。模型收益尚待实际采集、训练和完整评测。

最终 v4 将同样的一次自身工作集回收提前到模型加载完成后、模拟器构造前，以避免两者初始化驻留页峰值叠加。v3 已完成的一条76步成功采集轨迹和随后启动中断独立保留，均不并入 v4；v4 按原先声明的任务顺序重新采集。训练目标、任务划分、护栏、预算与截止时间不变，所有方法使用同一启动顺序。
